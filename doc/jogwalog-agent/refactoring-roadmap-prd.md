# PRD: React Native 앱 전체 리팩터링 로드맵

## 문제 정의

어장관리 앱은 AI 중심으로 빠르게 구현되어 주요 기능은 동작하지만, 현재 동작을 설명하고 보존할 수 있는 자동 테스트가 부족하다. 앱 코드에는 150줄 이상 파일이 40개 이상 존재하며, 핵심 화면 다수가 약 700줄에서 1,800줄 규모다. 화면 JSX, 스타일, 사용자 상호작용, 파생 상태, navigation, 서버 상태 연결이 한 파일에 함께 있어 변경 영향 범위를 판단하기 어렵다.

현재 자동 테스트는 순수 유틸리티 중심의 테스트 6개에 집중되어 있다. 화면, React Query hook, API 계약의 동작 보존 테스트가 부족하기 때문에 구조를 변경하면 사용자가 이용하던 흐름이 깨져도 빠르게 확인하기 어렵다.

이번 로드맵은 기능을 추가하거나 사용자 경험을 바꾸는 작업이 아니다. 현재 사용자 동작과 외부 계약을 테스트로 확인한 뒤, 사용자가 한 번에 검토할 수 있는 작은 단위로 앱 구조를 정리하는 작업이다.

## 해결 방향

리팩터링 전에 핵심 사용자 흐름과 레이어 계약을 동작 보존 테스트로 고정한다. 동작이 불명확하면 추측해서 테스트하지 않고, 사용자의 스모크 테스트로 현재 결과를 확인한 뒤 테스트를 작성한다.

앱 화면은 UI 조립과 표시 책임에 집중한다. 사용자 상호작용과 로컬 상태 수명주기는 기능별 hook, 서버 상태와 cache 관리는 React Query hook, Supabase와 외부 API 통신은 API 모듈, React와 무관한 도메인 규칙은 순수 유틸리티로 분리한다.

전체 리팩터링은 한 번에 실행하지 않는다. 모든 작업은 사용자가 명시적으로 지시한 뒤 하나씩 시작하며, 동작 설명, 테스트 추가, 사용자 승인, 구조 변경, 자동 검증, 사용자 스모크 테스트 순서로 진행한다.

## 사용자 시나리오

1. 앱 사용자는 리팩터링 전후에도 로그인, 조과 등록·수정·삭제, 조과 목록·상세 확인을 동일하게 이용하기를 원한다. 이를 통해 내부 구조 변경으로 개인 조과 기록이 손실되거나 잘못 표시되는 위험을 줄일 수 있다.
2. 앱 사용자는 리팩터링 전후에도 홈, 내 지도, 어종 도감, AI 어종 판별, 설정 화면의 기존 흐름을 동일하게 이용하기를 원한다. 이를 통해 구조 개선 과정에서도 익숙한 사용 경험을 유지할 수 있다.
3. 개발자는 핵심 사용자 흐름을 화면 통합 테스트로 확인하기를 원한다. 이를 통해 UI 구조를 변경해도 표시 상태, 입력, 버튼 동작, navigation 요청이 유지되는지 판단할 수 있다.
4. 개발자는 React Query hook의 loading, success, error, mutation 후 cache 동작을 테스트하기를 원한다. 이를 통해 서버 상태 연결을 변경해도 데이터 갱신 흐름을 보존할 수 있다.
5. 개발자는 API 경계의 입력 DTO 변환, Supabase 호출 계약, 반환값과 오류 변환을 테스트하기를 원한다. 이를 통해 내부 API 모듈을 분리해도 앱과 백엔드 사이의 계약을 유지할 수 있다.
6. 개발자는 순수 도메인 로직의 대표값, 경계값, 잘못된 입력을 테스트하기를 원한다. 이를 통해 UI에서 로직을 분리한 뒤에도 계산과 변환 결과를 신뢰할 수 있다.
7. 개발자는 카메라, 위치, 지도, 로그인처럼 네이티브 또는 외부 서비스에 의존하는 동작을 직접 스모크 테스트하기를 원한다. 이를 통해 복잡한 E2E 환경을 먼저 도입하지 않고도 실제 기기 동작을 확인할 수 있다.
8. 개발자는 각 리팩터링 작업을 시작하기 전에 대상 코드의 현재 동작과 문제를 설명받기를 원한다. 이를 통해 AI가 만든 코드를 이해하고 변경 범위를 직접 승인할 수 있다.
9. 개발자는 동작 보존 테스트가 준비된 후에만 리팩터링이 진행되기를 원한다. 이를 통해 구조 변경 전후 결과를 비교할 수 있다.
10. 개발자는 한 번에 하나의 작은 리팩터링 작업만 검토하기를 원한다. 이를 통해 변경 원인과 결과를 이해하고 스모크 테스트 범위를 통제할 수 있다.
11. 개발자는 150줄을 넘는 파일이 책임을 적절히 나누고 있는지 검토하기를 원한다. 이를 통해 줄 수를 맞추기 위한 무의미한 분리 없이 복잡한 파일을 식별할 수 있다.
12. 개발자는 자체 스타일 블록이 약 100줄을 넘는 경우 스타일 파일 분리를 검토하기를 원한다. 이를 통해 큰 표현 코드의 가독성을 개선하되 스타일 분리 자체를 책임 분리로 오해하지 않을 수 있다.
13. 개발자는 공통 hook이나 공통 컴포넌트 추출 여부를 직접 판단하기를 원한다. 이를 통해 성급한 공통화로 기능 간 결합도가 높아지는 것을 방지할 수 있다.
14. 개발자는 리팩터링 중 발견한 일반 버그와 UX 개선점을 별도 이슈로 관리하기를 원한다. 이를 통해 기능 변경과 구조 변경을 섞지 않고 검증할 수 있다.
15. 개발자는 데이터 손실, 보안 취약점, 앱 크래시를 발견하면 리팩터링보다 먼저 대응하기를 원한다. 이를 통해 개인 데이터와 앱 안정성을 우선 보호할 수 있다.
16. 개발자는 리팩터링 이슈 완료 시 lint, TypeScript 타입체크, 관련 자동 테스트 결과와 남은 수동 검증 범위를 확인하기를 원한다. 이를 통해 다음 작업을 시작할 근거를 확보할 수 있다.

## 구현 결정

- 이번 로드맵은 React Native 앱 코드만 대상으로 한다. Supabase Edge Function과 기존 migration 리팩터링은 제외한다.
- 기존 Supabase 스키마, RLS, Storage 정책, Edge Function 요청·응답, Expo Router 경로, navigation 동작, 사용자 문구와 화면 흐름을 유지한다.
- 내부 함수명, 내부 타입, 컴포넌트 props는 책임 분리에 필요하면 변경할 수 있다. 공개 계약 변경이 필요하면 별도 기능 또는 migration 이슈로 분리한다.
- 앱 라우트는 얇은 화면 조립과 navigation에 집중한다.
- 표현 중심 UI는 기능별 컴포넌트에 둔다.
- 사용자 상호작용과 로컬 상태 수명주기는 기능별 hook에 둔다.
- 서버 상태와 cache 관리는 React Query hook에 둔다.
- Supabase와 외부 API 호출은 API 모듈에 둔다.
- React와 무관한 도메인 규칙은 순수 유틸리티에 둔다.
- 포괄적인 service 레이어는 추가하지 않는다.
- 화면 전체 로직을 하나의 거대한 screen hook으로 옮기지 않는다. 독립적인 상호작용과 상태 수명주기별 hook을 우선하고, 필요한 경우 얇은 조립 hook을 둔다.
- 파일 150줄은 강제 제한이 아니라 책임 분리 검토 기준으로 사용한다. 응집도가 높은 타입, 정적 데이터, 테스트, 설정, 스타일은 유지 이유가 명확하면 기준을 넘을 수 있다.
- 스타일은 기본적으로 사용하는 컴포넌트와 같은 파일에 둔다. 자체 스타일 블록이 약 100줄을 넘으면 전용 스타일 파일 분리를 검토하고 사용자 승인 후 진행한다.
- 공통 hook과 공통 컴포넌트는 자동 추출하지 않는다. 후보를 발견하면 근거와 장단점을 설명하고 사용자 지시가 있을 때만 추출한다.
- 기능 내부의 명확한 책임을 위한 전용 컴포넌트와 hook 분리는 리팩터링 범위에 포함할 수 있다.
- 한 컴포넌트에서만 사용하는 타입은 컴포넌트 선언 위에 둔다. 두 곳 이상에서 공유하는 타입과 API 요청·응답·DTO 타입은 목적별 타입 모듈에 둔다.
- 값의 집합을 표현하는 타입은 `type`, 객체 구조를 표현하는 타입은 `interface`를 사용한다.
- 함수와 변수는 camelCase, React 컴포넌트는 PascalCase를 사용한다. 함수와 컴포넌트는 기본적으로 함수 표현식으로 작성한다.
- 큰 API 모듈은 단순 CRUD 종류가 아니라 독립적인 규칙, 데이터 계약, 실패 조건을 기준으로 분리한다.
- 공통 줄 수 검사 스크립트나 lint 제한은 추가하지 않는다. 각 이슈 시작과 완료 시 필요한 대상만 확인한다.
- 리팩터링은 공통 테스트 기반, 조과 데이터와 Query hook, 조과 등록, 조과 목록·상세, 홈, 내 지도, 어종 도감, AI 어종 판별, 설정·프로필·공지·정책, 인증·앱 루트, 잔여 앱 코드 순서로 진행한다.
- 모든 리팩터링 이슈는 사용자 승인 단계가 필요한 HITL 작업으로 진행한다.
- 각 이슈는 단일 책임과 사용자가 한 번에 검토 가능한 동작 흐름을 다룬다. 변경 파일은 가능하면 5개 안팎으로 제한하며 범위가 커지면 후속 이슈로 나눈다.
- 일반 버그와 UX 개선은 별도 이슈로 기록한다. 데이터 손실, 보안 취약점, 앱 크래시는 별도 긴급 이슈로 먼저 처리한다.

## 테스트 결정

- 테스트는 내부 구현 세부사항이 아니라 외부에서 관찰되는 동작과 레이어 계약을 검증한다.
- 핵심 사용자 흐름은 화면 통합 테스트로 보호한다.
- 서비스 로직과 React Query hook은 단위 테스트와 통합 테스트로 보호한다.
- 카메라, 위치, 지도, 로그인 등 네이티브·외부 연동은 사용자가 관리하는 스모크 테스트 체크리스트로 검증한다.
- 대규모 스냅샷 테스트는 사용하지 않는다.
- 화면 테스트는 표시 상태, 사용자 입력, 버튼 동작, navigation 요청을 검증한다.
- Query hook 테스트는 loading, success, error, mutation 후 cache 무효화를 검증한다.
- API 테스트는 입력 DTO 변환, Supabase 호출 계약, 반환값과 오류 변환을 검증한다.
- 순수 로직 테스트는 대표값, 경계값, 잘못된 입력을 검증한다.
- 스타일 구조와 내부 함수 호출 순서는 검증하지 않는다.
- 불명확한 현재 동작은 추측해서 테스트하지 않는다. 사용자 스모크 테스트로 확인한 뒤 동작 보존 테스트를 작성한다.
- 전체 커버리지 수치 목표는 두지 않는다. 각 대상의 핵심 동작과 계약이 테스트됐는지 평가한다.
- 각 리팩터링 이슈는 동작 설명, 동작 보존 테스트 추가, 사용자 승인, 리팩터링, 자동 검증, 사용자 스모크 테스트 순서로 진행한다.
- 각 이슈 완료 시 lint, TypeScript 타입체크, 관련 테스트를 실행하고 테스트되지 않은 동작과 수동 검증 범위를 기록한다.

## 범위 제외

- 신규 기능 개발
- 일반적인 UX 개선과 사용자 문구 변경
- 기존 버그를 리팩터링과 함께 수정하는 작업
- Supabase Edge Function 내부 리팩터링
- 기존 migration 파일 정리 또는 재작성
- Supabase 스키마, RLS, Storage 정책 변경
- 카메라, 위치, 지도, 로그인 흐름을 위한 자동 E2E 테스트 도입
- 전체 테스트 커버리지 퍼센트 목표
- 줄 수 제한을 위한 CI 또는 lint 규칙
- 사용자 승인 없는 공통 hook·컴포넌트 추출
- 리팩터링과 무관한 포맷팅, 의존성 업그레이드, 설정 변경

## 추가 메모

- 현재 기준선은 앱 코드의 150줄 이상 파일 40개 이상, 핵심 화면 약 700줄에서 1,800줄, 순수 유틸리티 자동 테스트 6개다.
- PRD에는 구조적 문제와 작업 원칙만 유지한다. 구체적인 파일별 문제와 분리 후보는 각 실행 이슈 시작 시 최신 코드를 기준으로 다시 조사한다.
- 사용자는 네이티브·외부 연동 스모크 테스트 체크리스트를 직접 작성하고 실행한다.
- PRD와 하위 이슈는 구현을 자동으로 시작시키지 않는다. 모든 이슈는 사용자의 명시적 지시 후 하나씩 진행한다.
